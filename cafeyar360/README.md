# کافه یار ۳۶۰ | Cafe Yar 360 Management

نسخه نامزد ۱.۴.۱ — تثبیت اسپرینت دوم روی شاخه `feature/sprint-2` در مخزن Nima؛ تأیید و ادغام در main هنوز انجام نشده است.

نام محصول **کافه یار ۳۶۰ (Cafe Yar 360)** است و **کافه نیما** نام کافه نمونه است. نام فایل‌ها، مسیرهای موجود و دیتابیس `cafe_nima.sqlite3` حفظ شده‌اند.

سامانه محلی مدیریت کافه با Python 3.11+، FastAPI، SQLite و رابط فارسی راست‌چین. این نسخه ادامه همان سورس کافه نیما است. پرداخت آنلاین متصل نیست؛ کارتخوان فقط به صورت دستی ثبت می‌شود. تحلیل مدیریتی قاعده‌محور است و API پولی ندارد.

## اجرای دمو در ویندوز

ZIP را استخراج و `run_windows.bat` را اجرا کنید. این راه‌انداز در صورت تنظیم‌نشدن `DEMO_MODE`، آن را برابر ۱ می‌گذارد؛ داده ساختگی و حساب‌های دمو ایجاد می‌شوند. نصب اولیه وابستگی‌ها اینترنت می‌خواهد. مرورگر و سرور بعداً روی شبکه محلی کار می‌کنند؛ ثبت سفارش بدون دسترسی به سرور کار نمی‌کند.

اجرای دستی در Windows CMD:

```bat
py -3 -m venv .venv
call .venv\Scripts\activate.bat
python -m pip install -r requirements-lock.txt
set DEMO_MODE=1
python manage.py init
python -m uvicorn app:app --host 127.0.0.1 --port 8000
```

لینوکس/macOS:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-lock.txt
export DEMO_MODE=1
python manage.py init
python -m uvicorn app:app --host 127.0.0.1 --port 8000
```

آدرس دمو: http://127.0.0.1:8000/presentation و منوی میز ۳: http://127.0.0.1:8000/menu?table=3

نام حساب‌های اولیه مدیر `admin`، صندوق `cashier` و باریستا `barista` است. **رمز ثابت نمایشی وجود ندارد**؛ `manage.py init` در اولین اجرا رمزهای حداقل ۱۲کاراکتری را به‌صورت مخفی می‌پرسد، یا آن‌ها را از سه متغیر `CAFE_PASSWORD_*` می‌خواند. رمز در فایل یا گزارش نوشته نمی‌شود. دکمه‌های ورود فقط نام کاربری را پر می‌کنند.

## شبکه محلی و تنظیمات

برای استفاده گوشی، `PUBLIC_BASE_URL` را IP واقعی سرور قرار دهید و uvicorn را با `--host 0.0.0.0` اجرا کنید. گوشی و سرور باید به هم دسترسی داشته باشند؛ Firewall پورت ۸۰۰۰ را فقط روی شبکه مورد اعتماد مجاز کند. QR در `/admin` ساخته می‌شود. `127.0.0.1` برای QR گوشی مناسب نیست.

`.env.example` فقط مستند متغیرهاست؛ برنامه فایل `.env` را خودکار بارگذاری نمی‌کند. متغیرها را در shell تنظیم کنید. توکن تلگرام فقط در متغیر محیطی باشد و در فایل نوشته نشود.

| متغیر | رفتار |
|---|---|
| `DEMO_MODE` | پیش‌فرض برنامه ۰؛ مقدار ۱ صریحاً نمونه ساختگی و حساب دمو را مجاز می‌کند |
| `CAFE_DB_PATH` | مسیر DB؛ پیش‌فرض `cafe_nima.sqlite3` کنار برنامه؛ نام قدیمی برای سازگاری حفظ شده |
| `CAFE_PASSWORD_ADMIN` / `CAFE_PASSWORD_CASHIER` / `CAFE_PASSWORD_BARISTA` | ساخت اولیه هر DB، نمایشی یا غیرنمایشی؛ حداقل ۱۲ کاراکتر، از محیط امن یا ورودی مخفی |
| `PUBLIC_BASE_URL` | آدرس پایه برای QR گوشی؛ مثلاً `http://192.168.1.20:8000` |
| `COOKIE_SECURE` | ۰ برای HTTP محلی؛ ۱ برای HTTPS؛ با ۱ نشست روی HTTP ارسال نمی‌شود |
| `TELEGRAM_BOT_TOKEN` | اختیاری، فقط محیط فرآیند بات |

برای DB غیرنمایشی، `DEMO_MODE=0` و سه رمز قوی متفاوت را خصوصی تنظیم کنید، سپس `python manage.py init` را اجرا کنید. در این حالت فقط schema و سه حساب ایجاد می‌شوند؛ محصول، مشتری، سفارش و داده مالی نمونه درج نمی‌شود. راه‌اندازی بدون رمزهای لازم متوقف می‌شود. مدیریت کامل میز/کاربر و onboarding دیتابیس خالی هنوز تکمیل نشده‌اند؛ این حالت به معنای آمادگی کامل بهره‌برداری نیست.

تغییر متغیر رمز، رمز DB موجود را عوض نمی‌کند. برای تغییر رمز و ابطال نشست‌های همان حساب:

```bash
python manage.py password admin
python manage.py password cashier
python manage.py password barista
```

رمز جدید به صورت مخفی پرسیده می‌شود و وارد آرگومان دستور، کد یا Git نمی‌شود. اگر DB قبلی رمز عمومی داشته باشد، startup غیرنمایشی متوقف می‌شود تا با همین ابزار رمزها عوض شوند. تغییر حالت دمو به عملیاتی داده‌های قبلی را پاک نمی‌کند؛ برای داده واقعی DB جدا بسازید.

## دیتابیس و مهاجرت

```bash
python manage.py init
python manage.py backup backups/before-upgrade.sqlite3
```

فایل مقصد backup باید جدید باشد. ابزار از SQLite backup API استفاده می‌کند؛ فایل DB فعال در حالت WAL را دستی کپی نکنید. برای بازیابی، وب و بات را متوقف کنید و بکاپ را در مسیر **جدید و خالی** بگذارید، سپس `CAFE_DB_PATH` را به آن تغییر دهید. ابتدا روی کپی تست کنید؛ بکاپ شامل اطلاعات خصوصی است و نباید وارد Git شود.

`manage.py init` و startup مهاجرت افزایشی انجام می‌دهند. جدول `order_materials` مقدار مواد سفارش را ثابت نگه می‌دارد؛ تغییر رسپی یا حذف افزودنی مصرف سفارش ثبت‌شده را تغییر نمی‌دهد. سفارش بازِ قدیمی هنگام اولین ارتقا بر مبنای رسپی همان لحظه snapshot می‌شود؛ اطلاعات تاریخی حذف‌شده قابل بازسازی نیست. کلید درخواست سفارش قدیمی که hash ندارد، با پاسخ ۴۰۹ به retry جواب می‌دهد تا رسید نامرتبط برنگردد.

مصرف و قیمت‌گذاری مواد همچنان هنگام `completed` انجام می‌شود؛ رزرو موجودی و بهای میانگین خرید پیاده نشده‌اند. نسخه data-free ساختار در `docs/schema.sql` است؛ راه پشتیبانی‌شده ساخت و ارتقا، `manage.py init` است. DB نمونه را با `DEMO_MODE=1` بسازید؛ هیچ DB در Git نگهداری نمی‌شود.

## آنچه اکنون کار می‌کند

- مشتری: دسته‌بندی، افزودنی، QR میز، سفارش، حساسیت غذایی، پیگیری توکن‌دار و ارسال به صف کارکنان.
- کارکنان: نقش staff، پذیرش همراه تأیید حساسیت، آماده‌سازی و تحویل؛ صف فعال مستقل از محدودیت تاریخچه.
- صندوق: تسویه نقدی/کارتخوان دستی با تراکنش و قید یکتا، رد پرداخت تکراری و لغو سفارش تسویه‌شده؛ صف همه تسویه‌نشده‌ها، رسید چاپی، گزارش مغایرت و اصلاح روش با مجوز مدیر و سابقه.
- انبار: محصول و مواد و رسپی، خرید، اصلاح موجودی، مصرف از snapshot سفارش و بهای مصرف.
- مدیریت: فروش تحویل‌شده، دریافتی، بهای مصرف، سود ناخالص، میانگین مبلغ، فروش روزانه/ماهانه و فیلتر تاریخ؛ تحلیل قاعده‌محور.
- CRM: رضایت باشگاه، پرونده، یادداشت و مجموع خرید؛ تاریخچه تفصیلی و بخش‌بندی وفاداری هنوز کامل نیست.
- تردد: ورود/خروج معتبر، سابقه مدیر و مشاهده فقط سابقه خود برای کارمند؛ اتصال یک‌بارمصرف تلگرام و دستورات بات.

ثبت سفارش با همان کلید و payload یکسان همان رسید قبلی را برمی‌گرداند؛ payload متفاوت پاسخ ۴۰۹ دارد. کلید را پس از خطای شبکه بی‌دلیل عوض نکنید. تاریخچه API با `GET /api/orders?limit=100&offset=0` صفحه‌بندی می‌شود؛ صف‌های عملیاتی `queue=active` و `queue=unpaid` مستقل‌اند.

## تلگرام

پس از تنظیم خصوصی `TELEGRAM_BOT_TOKEN` و همان `CAFE_DB_PATH`، در فرآیند جدا `python telegram_bot.py` را اجرا کنید؛ یا از راه‌اندازهای `run_*_with_telegram` استفاده کنید که توکن را مخفی می‌پرسند و فقط به محیط فرزند می‌دهند. پنل `/attendance` کد اتصال ۱۰ دقیقه‌ای می‌دهد. کارمند در چت خصوصی `/link CODE`، سپس `/in` و `/out` می‌فرستد. بدون اتصال، ثبت بات مجاز نیست. اینترنت فقط برای بات لازم است.

تست‌های تلگرام آفلاین و با mock شبکه‌اند؛ اتصال زنده، بازیابی offset، گزارش ساعت کار و مدیریت شیفت در این اسپرینت تکمیل نشده‌اند.

## تست و سناریوی ارائه

```bash
python -m pip install -r requirements-lock.txt
python -m pytest -q
```

مبنای انتقال نسخه ۱.۴ شامل ۶۳ تست موفق بود. نامزد ۱.۴.۱ شامل ۷۰ تست موفق روی Linux/Python 3.12. هشدار deprecation مربوط به TestClient نسخه Starlette موجود است. workflow فعال پروژه در ریشه مخزن فقط مسیر cafeyar360 را برای Windows/Ubuntu و Python 3.11/3.12 بررسی می‌کند؛ نتیجه واقعی Actions در PR و گزارش تحویل ثبت می‌شود. موفقیت محلی به‌تنهایی تأیید ویندوز نیست.

برای ارائه: در `/menu?table=3` سفارش ثبت کنید؛ با barista در `/staff` تا تحویل پیش بروید؛ با cashier در `/cashier` ابتدا شیفت را باز و سپس نقدی یا کارتخوان ثبت کنید؛ با admin در `/inventory`، `/finance`، `/analytics` و `/crm` نتایج را ببینید. در `/attendance` ورود و خروج ثبت کنید. این سناریو از APIها و DB واقعی همین نسخه استفاده می‌کند.

## موارد باقی‌مانده

محصول هنوز کامل نیست. افزایش مبلغ/قیمت پس از تسویه، تاریخچه و وفاداری CRM، ساعت کار کارکنان، مدیریت کامل کاربر/میز و سخت‌سازی امنیتی باقی مانده‌اند. شیفت صندوق و ثبت دستی استرداد کامل/جزئی اکنون پیاده شده‌اند. اصلاح روش پرداخت در این نسخه مبلغ را تغییر نمی‌دهد و ثبت/بستن مغایرت به معنی برگشت وجه یا ثبت سند اصلاح مبلغ نیست.

محدودیت تلاش ورود، بررسی CSRF، HTTPS استقرار، سیاست نگهداری اطلاعات، backup خودکار، بارسنجی و offset پایدار تلگرام هنوز تکمیل نشده‌اند. این نسخه را به اینترنت عمومی منتشر نکنید. کارتخوان مستقیم، پرداخت آنلاین و حسابداری رسمی ادعا نمی‌شوند.

جزئیات تغییرات، ریسک‌ها و rollback: [اسپرینت دوم](docs/SPRINT-02-FA.md) و [اسپرینت اول](docs/SPRINT-01-FA.md). راهنمای انتشار: [GITHUB-SETUP-FA.md](GITHUB-SETUP-FA.md).

## صندوق، شیفت و استرداد — نسخه ۱.۴

در `/cashier` ابتدا موجودی نقد شمارش‌شده افتتاحیه را وارد و شیفت را باز کنید. در هر لحظه یک شیفت مشترک باز است؛ هر عملیات عامل خودش را دارد. مسئول افتتاح یا مدیر می‌تواند با شمارش واقعی، شیفت را ببندد؛ برای اختلاف، توضیح الزامی است. شیفت بسته بازنویسی نمی‌شود.

انتظار نقد = افتتاحیه + دریافت نقد − استرداد نقد − هزینه/خریدی که **صریحاً از صندوق** پرداخت شده است؛ کارتخوان جدا گزارش می‌شود. هزینه معمولی از صندوق نقد کم نمی‌شود مگر `from_drawer=true`. وجه نقد منفی مجاز نیست؛ کمبود نقد یا موجودی مواد پاسخ ۴۰۹ می‌دهد و کل عملیات rollback می‌شود.

خارج از شیفت، مدیر می‌تواند هماهنگی حضوری یا شماره تیکت و دلیل را برای ثبت مستقیم وارد کند؛ صندوق‌دار درخواست می‌فرستد و مدیر تأیید/رد می‌کند. درخواست تا تأیید اثر مالی ندارد و هنگام تأیید دوباره اعتبارسنجی می‌شود. کارمند معمولی اجازه عملیات مالی ندارد. سامانه تیکت مستقل یا اتصال سرویس تیکت وجود ندارد؛ مرجع تیکت مستند داخلی است.

عملیات خارج از شیفت در دفتر استثناها می‌مانند. موجودی افتتاحیه شیفت بعد، شمارش واقعی **پس از آن عملیات** است؛ مبلغ آن‌ها دوباره به افتتاحیه اضافه نمی‌شود. برای سوابق قبل از این نسخه هیچ شیفت یا گردش نقد ساختگی ایجاد نمی‌شود. اصلاح روش پرداخت متعلق به شیفت بسته/قدیمی، سابقه اصلاح دارد ولی مانده شیفت بسته و وجه نقد شیفت جدید را تغییر نمی‌دهد.

از تاریخچه کامل و صفحه‌بندی‌شده صندوق، رسید و استرداد قابل دسترسی‌اند. وضعیت مالی از وضعیت آماده‌سازی جداست: تسویه‌نشده، تسویه‌شده، استرداد جزئی و استرداد کامل. صندوق‌دار می‌تواند درخواست اصلاح یا استرداد بفرستد؛ ثبت مستقیم آن‌ها فقط مدیر است. فیلتر وضعیت مالی روی کل تاریخچه اعمال می‌شود، سپس صفحه‌بندی می‌شود.

استرداد کامل/جزئی با مبلغ، روش واقعی برگشت وجه، دلیل، ثبت‌کننده، نسخه پرداخت و کلید تکرار ثبت می‌شود. پرداخت اصلی حذف نمی‌شود؛ افزایش مبلغ و پرداخت دوم روی همان سفارش مجاز نیست. استرداد بدهی جدید برای مشتری نمی‌سازد. ثبت دستی برگشت کارتخوان به معنی انتقال بانکی خودکار نیست.

- استرداد جزئی پیش از تحویل، سفارش را فعال نگه می‌دارد و هنگام تحویل از فروش آن کم می‌شود.
- استرداد کامل پیش از تحویل، سفارش را لغو می‌کند. اگر آماده‌سازی شروع شده باشد، مواد snapshot فقط یک بار مصرف و هزینه آن ضایعات می‌شود. اگر مواد کافی نباشد، عملیات یکپارچه رد می‌شود؛ ابتدا موجودی واقعی بررسی و اصلاح شود.
- استرداد پس از تحویل از فروش در تاریخ استرداد کم می‌شود؛ بهای مواد مصرف‌شده باقی می‌ماند و موجودی خودکار برنمی‌گردد.
- اصلاح روش/پیگیری با سابقه قبل/بعد ثبت می‌شود؛ برای کاهش مبلغ از استرداد استفاده کنید.

رسید پرداخت از `/receipts/{order_id}` و رسید یک استرداد از همان مسیر با `?refund_id={id}` چاپ می‌شود. JSON رسید `/api/orders/{id}/receipt` تاریخچه اصلاح و استرداد و مانده قابل استرداد را دارد؛ اطلاعات تماس مشتری در رسید نیست. نام کافه نمونه و محصول هر دو نمایش داده می‌شوند. چاپ مرورگر/PDF تست شده؛ چاپگر فیزیکی و فاکتور رسمی مالیاتی ادعا نمی‌شوند.

## دقت عددی و مبنای گزارش

مبلغ‌های حسابداری با عدد صحیح در **یک‌صدم تومان** (نه ریال) ذخیره می‌شوند؛ فیلدهای `*_minor` مرجع دقیق‌اند. ستون‌های قدیمی برای سازگاری حفظ می‌شوند. ورودی مبالغ جدید حداکثر دو رقم اعشار دارد؛ مقدار مواد حداکثر شش رقم. بهای کل مواد هر سفارش با Decimal محاسبه و فقط در پایان با ROUND_HALF_UP به یک‌صدم تومان گرد می‌شود. مبالغ تکی حداکثر ۹٬۰۰۰٬۰۰۰٬۰۰۰٬۰۰۰ تومان‌اند.

`summary.gross_sales` فروش ناخالص سفارش تحویل‌شده، `sales_returns` استرداد/کاهش شناسایی‌شده، `revenue` فروش خالص و `cogs` بهای همان سفارش‌های تحویل‌شده است. سود ناخالص = فروش خالص − بهای مصرف. ضایعات آماده‌سازی جدا از COGS نشان داده و در سود عملیاتی تخمینی کم می‌شود. خرید انبار دوباره از سود کم نمی‌شود.

`cash_received` دریافت وجه و `cash_refunded` خروج وجه استردادی در تاریخ عملیات‌اند. پیش‌دریافت سود نمی‌سازد. استردادِ دوره بعد، فروش ناخالص و COGS دوره قبلی را بازنویسی نمی‌کند. میانگین مبلغ، فروش خالص دوره تقسیم بر تعداد تحویل‌های دوره، با گردکردن دو رقم اعشار است؛ دوره بدون تحویل، میانگین صفر دارد.

`receivables` و `advances` وضعیت **فعلی** سفارش‌های مرتبط با بازه‌اند، نه تراز تاریخی در پایان آن روز. `order_states` وضعیت فعلی مالی و آماده‌سازی سفارش‌هایی است که در بازه ثبت شده‌اند؛ بنابراین شمار تحویل این گروه ممکن است با شمار تحویل‌های انجام‌شده در بازه متفاوت باشد.

APIهای `/api/finance` و `/api/analytics` پارامترهای فراگیر `start` و `end` با تاریخ ISO میلادی می‌پذیرند. ورودی تاریخ رابط همچنان میلادی است؛ **نمایش، تجمیع روز/هفته/ماه و رسید شمسی و ساعت تهران** است. هفته از شنبه شروع می‌شود. تاریخ‌های قدیمی دارای offset به تهران تبدیل می‌شوند؛ تاریخ قدیمی بدون offset، زمان تهران فرض می‌شود. سری‌های گزارش تمام نقاط دارای رویداد را برمی‌گردانند؛ نمودار رابط آخرین ۱۴ روز و ۱۲ هفته/ماه را نشان می‌دهد. دوره بدون رویداد با صفر پر نمی‌شود؛ برگشت فروش می‌تواند ستون منفی ایجاد کند.

## APIهای مالی جدید

| عملیات | مسیر و نقش |
|---|---|
| افتتاح / فهرست شیفت | `POST /api/cashier/shifts` و `GET /api/cashier/shifts`؛ مدیر/صندوق |
| بستن شیفت | `POST /api/cashier/shifts/{id}/close`؛ مسئول شیفت یا مدیر |
| پرداخت | مسیر موجود `POST /api/orders/{id}/pay`؛ اکنون شیفت یا هماهنگی لازم دارد |
| استرداد / مشاهده سوابق | `POST /api/payments/{id}/refunds` فقط مدیر؛ `GET` مدیر/صندوق |
| اصلاح روش | مسیر موجود `PATCH /api/payments/{id}/correction` فقط مدیر |
| درخواست هماهنگی | `POST/GET /api/cashier/requests`؛ صندوق فقط درخواست‌های خودش را می‌بیند |
| تأیید یا رد | `PATCH /api/cashier/requests/{id}/review` فقط مدیر |
| دفتر استثنا | `GET /api/cashier/exceptions` فقط مدیر |
| تاریخچه پرداخت | `GET /api/cashier/payments?payment_status=all&limit=20&offset=0`؛ مدیر/صندوق |

نمونه افتتاح: `{"opening_amount":"1000.25","idempotency_key":"demo-shift-open-01"}`.

نمونه بستن: `{"counted_amount":"1000.25","note":"شمارش پایان شیفت"}`.

نمونه استرداد: `{"amount":"1000.25","method":"cash","reason":"جبران سفارش نمونه","reference":"DEMO-REF","expected_revision":0,"idempotency_key":"demo-refund-01"}`.

ثبت مستقیم مدیر خارج از شیفت، فیلد `authorization` لازم دارد: `{"coordination":"ticket","reference":"DEMO-TICKET","reason":"هماهنگی نمونه"}`؛ نوع `in_person` به جای ticket نیز مجاز است.

درخواست دارای `kind` برابر payment/refund/correction، `target_id` (شناسه سفارش برای payment و شناسه پرداخت برای دو مورد دیگر)، `payload` مطابق عملیات، `coordination`، `reference`، `reason` و `idempotency_key` است. بررسی مدیر `{"decision":"approved","resolution":"تأیید هماهنگی نمونه"}` یا rejected می‌پذیرد. رد، اثر مالی ندارد؛ درخواست قدیمی/نامعتبر هنگام تأیید ۴۰۹ می‌گیرد و در انتظار می‌ماند تا رد یا درخواست تازه ثبت شود.

کلید استرداد و درخواست و افتتاح الزامی است؛ استفاده مجدد از همان کلید با داده متفاوت پاسخ ۴۰۹ می‌گیرد. برای هزینه و خرید، `idempotency_key` اختیاری برای سازگاری API قدیمی است؛ **برای retry حتماً آن را بفرستید**. رابط کلید می‌فرستد و در قطع پاسخ، بسته نامشخص استرداد/درخواست/هزینه/خرید را در sessionStorage برای retry همان عملیات نگه می‌دارد. تغییر عمدی داده‌ها پس از پاسخ خطا، عملیات تازه محسوب می‌شود؛ ابتدا رسید قبلی بررسی شود.

## ارتقا، تست و تحویل

پیش از ارتقا، از SQLite backup API با `python manage.py backup backups/before-upgrade.sqlite3` استفاده کنید. migration نسخه ۳ افزایشی است و شماره سفارش/پرداخت و مقادیر اصلی تاریخی را حفظ می‌کند؛ shadow مبلغ قدیمی به دو رقم اعشار گرد می‌شود. نویز باینری بسیار کوچک مقدار مواد تا شش رقم اصلاح می‌شود؛ دقت تاریخیِ واقعاً بیشتر از شش رقم یا مبلغ منفی، ارتقا را برای بررسی روی کپی متوقف می‌کند.

برای دموی تازه، همان `DEMO_MODE=1` و `python manage.py init` کافی است. نام پیش‌فرض DB همچنان `cafe_nima.sqlite3` است. ابتدا در صندوق شیفت باز کنید، سپس سفارش را تسویه و مراحل تحویل، استرداد و چاپ را نمایش دهید. برای نمایش درخواست خارج از شیفت، شیفت را ببندید، با صندوق‌دار درخواست ثبت و با مدیر تأیید کنید.

`python -m pytest -q` مجموعه ۶۳ تست را اجرا می‌کند. `npm run test:browser` جریان مشتری/کارکنان/تسویه را و `node tests/browser-finance.cjs` شیفت، اصلاح، استرداد، قطع پاسخ پس از ثبت استرداد و retry، تأیید درخواست، رسید/PDF و گزارش موبایل را آزمایش می‌کند. برای تست مرورگر، uvicorn آزمایشی باید روی ۸۰۱۰ با DB نمونه جدا اجرا شود؛ اسکریپت‌ها داده آزمایشی می‌سازند. خروجی‌ها در `test-artifacts/` و خارج از Git هستند.

نسخه‌های تحویل در پوشه Drive اصلی با نام بسته نسخه جدا نگهداری می‌شوند: https://drive.google.com/drive/folders/1NArzX1JX6zGgmn3oxnisgBdX-yPSbR0S . فایل‌های قبلی جایگزین نمی‌شوند. مرجع GitHub اکنون https://github.com/nimahani70-create/Nima/tree/main/cafeyar360 است. این نسخه پیش از تأیید مالک فقط نامزد است؛ خروجی آن در پوشه review قرار می‌گیرد و بسته رسمی main پس از تأیید/ادغام ساخته می‌شود.

## راه‌اندازی امن و تست نامزد ۱.۴.۱

راه‌اندازهای Windows و Linux ابتدا `manage.py init` را اجرا می‌کنند؛ برای DB تازه و محیط تعاملی، رمزها مخفی پرسیده می‌شوند. در محیط غیرتعاملی سه متغیر رمز الزامی‌اند و نبود آن‌ها به خطای روشن منجر می‌شود؛ رمز تصادفیِ ناشناخته یا عمومی به‌طور پنهان جایگزین نمی‌شود. مقدار `DEMO_MODE=1` فقط داده ساختگی را فعال می‌کند، نه رمز ضعیف.

اگر DB قدیمی رمز عمومی داشته باشد، حتی در حالت دمو startup متوقف می‌شود؛ با `python manage.py password USERNAME` آن حساب را تغییر رمز دهید. ابزار پیش از تغییر رمز و پیش از init روی DB موجود، snapshot سازگار SQLite در `backups/` می‌سازد؛ نسخه‌های قبلی overwrite نمی‌شوند. نسخه پشتیبان ممکن است داده خصوصی داشته باشد و نباید وارد Git یا خروجی عمومی شود.

DB نمونه review با داده ساختگی و hash رمزهای تصادفیِ افشانشده‌نشده تحویل می‌شود. برای استفاده، روی کپی محلی و پیش از راه‌اندازی، رمز حساب‌های admin/cashier/barista را با ابزار password تنظیم کنید. هیچ فایل رمز همراه نمونه تحویل نمی‌شود. توکن تلگرام فقط محیط است و آزمون زنده بدون توکن و محیط آزمایشی مجاز انجام نمی‌شود.

تست‌های Python اعتبارنامه‌های صریحاً ساختگی در fixture دارند؛ کلاینت تست مرورگر رمزها را از محیط می‌خواند و داخل JavaScript اجرایی یا گزارش ذخیره نمی‌کند. برای مرورگر از DB تازه و جدا استفاده کنید؛ `CAFE_TEST_BASE_URL` پیش‌فرض http://127.0.0.1:8010 است و برای حفظ دموی در حال اجرا می‌تواند به پورت آزمایشی دیگر اشاره کند. اسکریپت‌ها در نبود رمزهای آزمایشی معتبر متوقف می‌شوند. تست‌ها را روی داده واقعی اجرا نکنید.

دستور تست: `python -m pytest -q --junitxml=pytest-results.xml`. تست مرورگر: `npm ci`، `npx playwright install chromium`، سپس `npm run test:browser` و `node tests/browser-finance.cjs` روی سرور موقت با رمزهای محیطی. CI همین دو سناریو را با DB موقت و رمزهای تصادفی مخفی‌شده اجرا می‌کند؛ DB و log خام در artifact عمومی نیستند.

حذف رمزهای ثابت از نسخه جدید، آن‌ها را از commitهای عمومی قدیمی پاک نمی‌کند. Force Push انجام نمی‌شود؛ راه امن، تعویض رمز حساب‌های محلی و استفاده از راه‌اندازی جدید است. CSRF، محدودیت ورود و مدیریت پرسنل در اسپرینت سوم و پس از تأیید/ادغام این PR انجام خواهند شد؛ این نامزد ادعای تکمیل آن قابلیت‌ها ندارد.
